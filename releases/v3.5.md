# MOSA Framework v3.5

Release date: 2026-06-04

MOSA v3.5 focuses on reducing over-orchestration while keeping the framework's routing, proof, and audit strengths. The headline change is proportional activation: MOSA now chooses between Lean, Standard, and Cold-repair modes instead of running every layer for every task.

## Highlights

- Added Lean Mode for simple Q&A, direct checks, and tiny obvious edits.
- Added Standard Mode for multi-step, file-changing, routable, or auditable work.
- Added Cold-repair Mode for new or damaged workspaces with missing or stale MOSA evidence.
- Hardened Router proof with a formal `routing_result.json` schema.
- Made `mosa_route.js` the official Router proof generator.
- Kept `mosa_search.js` as the internal search engine and emergency fallback.
- Added compact cold provision output by default.
- Added `--verbose` for debugging nested startup and route JSON.
- Updated README to match MOSA v3.5 behavior.
- Added token efficiency and Lean Mode simplification reports.

## Why This Release

Earlier MOSA versions were effective for long-running framework work, but the startup path had become too heavy for small tasks. v3.5 fixes that by making activation proportional to task complexity.

The goal is:

```text
simple task -> answer directly
multi-step task -> use startup proof and Router proof
broken or new workspace -> repair evidence first
```

## New Runtime Modes

| Mode | Use when | Skips |
| --- | --- | --- |
| `lean` | Simple Q&A, direct checks, tiny obvious edits | startup, Router, hooks, task-state writes |
| `standard` | Multi-step work, file changes, MOSA/skill/routing/graph/hook/registry/audit work | full registry diagnostics |
| `cold-repair` | New or damaged workspace; startup or Router proof missing/stale | broad model-side registry reads |

## Router Proof Hardening

`00_System/mosa_route.js` is now the official Router proof wrapper.

Valid Router proof is written to:

```text
01_Work/routing_result.json
```

The proof now includes:

- `schema_version`
- `status`
- `source`
- `created_at`
- `intent_hash`
- `input`
- `top_skill`
- `candidates`
- `fallback_code`
- `fallback_recommendation`
- `validation`

This prevents stale, reconstructed, or chat-only Router decisions from being treated as valid execution proof.

## Confidence Tiers

| Tier | Confidence | Behavior |
| --- | ---: | --- |
| `strong` | `>= 0.80` | Auto-dispatch allowed after proof validation |
| `medium` | `0.50-0.79` | Orchestrator review before dispatch |
| `weak` | `0.35-0.49` | Do not auto-dispatch |
| `fail` | `< 0.35` | Reroute, clarify, or run diagnostics |

Fallback codes include:

- `LOW_CONFIDENCE`
- `WEAK_CONFIDENCE`
- `NO_CANDIDATE`
- `MISSING_INDEX`
- `STALE_CACHE`
- `INVALID_SKILL_PATH`
- `ROUTER_ERROR`

## Token Efficiency

Normal model-visible startup is now expected to stay compact:

| Artifact | Approx tokens | Exposure |
| --- | ---: | --- |
| `01_Work/startup_result.json` | ~300 | Model reads |
| `01_Work/context_bus.json` | ~200 | Model reads |
| `01_Work/routing_result.json` | ~700 | Model reads |
| `02_Output/routing_index_light.json` | ~4,500 | Node reads |
| `02_Output/registry_distiller_report.json` | ~70,000+ | Cold diagnostics only |

Practical standard startup plus route proof is about 1,200 model-visible tokens when the Token Shield is followed.

## Compact Cold Provision

Cold provision now prints compact pointers by default:

```bash
node 00_System/mosa_provision_workspace.js --target "<workspace>" --run --intent "<task intent>"
```

Use `--verbose` only when full nested startup and route JSON is needed:

```bash
node 00_System/mosa_provision_workspace.js --target "<workspace>" --run --verbose --intent "<task intent>"
```

Full evidence is still written to:

```text
01_Work/provision_result.json
```

## Event-Triggered Hooks

Routine tasks do not run full hook chains.

Default routine command:

```bash
node 00_System/mosa_hooks.js --level auto --event normal-task
```

P2 remains required before trusting framework updates.

## Upgrade Notes

Use the v3.5 protocol in `AGENTS.md` as authoritative.

For simple work, do not activate the full MOSA chain. Use Lean Mode.

For framework, routing, skill, registry, hook, graph, audit, or multi-step work, use Standard Mode.

For new or broken workspaces, use Cold-repair Mode.
